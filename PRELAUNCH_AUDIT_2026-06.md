# SMAART Platform — Pre-Launch Audit Report
**Date:** 2026-06-09  |  **Branch:** vickram  |  **Audited by:** multi-agent audit teams (16 finder agents + adversarial verification)

---

## Executive Summary

A full-codebase audit was run across the backend (Express/Mongoose, 322 JS files, 50+ routes, 50+ models), the frontend (React 19/Vite, 279 components/pages), and the AWS/Docker deployment configuration.

**163 raw findings** were produced; the **59 critical/high** items were each independently re-verified against the source code. **56 were confirmed, 3 refuted** (removed as false positives). Below are the verified results.

| Severity | Count | Meaning |
|---|---:|---|
| 🔴 **Critical** | 12 | Exploitable now; **block deployment** until fixed |
| 🟠 **High** | 21 | Fix before public launch |
| 🟡 **Medium** | 22 (+ medium/low pool) | First hardening sprint |
| ⚪ **Low** | — | Backlog |

### The headline problem: broken authentication & authorization
The single most serious theme is that **multiple route files have NO authentication at all**. `students.js`, `teachers.js`, and `coaches.js` expose full unauthenticated CRUD over staff and student PII — anyone on the internet can dump your entire student database, create rogue accounts, or delete records. Worse, `users.js` lets an attacker **reset any user's password by posting their email** (full account takeover). These must be fixed before the app is reachable from the internet.

### The second headline: leaked production secrets
`back-end/.env` and `back-end/.env.backup` are **committed to git**. They contain live MongoDB Atlas credentials, the JWT secret, Cloudinary, SMTP, OpenRouter, Deepgram and ITSM keys. The `.gitignore` rule does not help because the files were already tracked. **Every one of these secrets must be rotated** — deleting the file is not enough; they live in git history.

### Deployment verdict
Your choice of **Docker on AWS ECS Fargate in Mumbai (ap-south-1)** is the right call and is endorsed below. The deployment config is mostly sound (a `.dockerignore` correctly excludes secrets, ECS uses Secrets Manager ARNs), but there are real hardening gaps: JWT-in-websocket-URL (logged in plaintext), `:latest` mutable image tags, writable root filesystem, and an overly-open MongoDB network rule.

### 1. [CRITICAL] students.js routes are completely unauthenticated — full CRUD on all student PII and accounts
- **Category:** authorization
- **Location:** `back-end/routes/students.js:10-232`
- **Problem:** None of the routes in students.js apply the protect or requireRole middleware. Anyone can GET /students/ to enumerate every student (name, email, studentId, college), GET /students/:id and /students/by-email/:email to read arbitrary student records, POST / to create students, PUT /:id to modify any student (changing assignedTeacher, college, status, etc.), and DELETE /:id to delete any student. This is a complete IDOR + missing-auth disaster: an unauthenticated attacker can dump the entire student database and tamper with or delete any record. The .select('-password') only hides the hash; everything else is fully exposed and writable.
- **Fix:** Add `const { protect } = require('../middleware/auth'); const { requireRole } = require('../middleware/roleMiddleware');` and apply `router.use(protect);`. Gate listing/read/update/create/delete behind `requireRole('admin','teacher')` as appropriate, and for the self-service reads scope the query to req.user (e.g. a student may only fetch their own record: compare req.params.id to String(req.user._id)). Remove or admin-gate the by-email and studentId lookups since they enable enumeration.
  - **Verification:** confirmed (confidence: high). Confirmed in code. back-end/routes/students.js applies only generalLimiter (line 6) and registers every route with no protect/requireRole auth middleware: GET / (line 10, enumerate all students with name/email/studentId/college), GET /by-email/:email (62), GET /:id (93), GET /studentId/:studentId (123), POST / (153, create), PUT /:id (177, arbitrary update), DELETE /:id (210, delete). server.js:148 mounts it at /api/students with no middleware at the mount point either, so the routes are fully unauthenticated. .select('-password') only strips the hash; all other PII is readable, and PUT/POST/DELETE allow tampering and deletion. PUT does delete req.body.password (line 180), but college/status/assignedTeacher etc. remain freely writable. This is a genuine missing-auth + IDOR exposure of student PII and write access. Critical severity is appropriate.

### 3. [CRITICAL] users.js sensitive endpoints (register-details, register-section, login, register-details/:email) are unauthenticated and allow account takeover / cross-user data write
- **Category:** authorization
- **Location:** `back-end/routes/users.js:71-849`
- **Problem:** POST /register-details, PATCH /register-section, POST /login, POST /create, and GET /register-details/:email have no protect middleware. register-details and register-section accept an arbitrary `email` in the body and will create or overwrite the User/Student/Registration record for that email — including setting a `password` (users.js:152-165, 230) — so an attacker can overwrite any victim's password by posting their email, achieving full account takeover. GET /register-details/:email returns the full registration/user object (toObject at 774, 825, 837) for any email, exposing PII to anyone.
- **Fix:** Require `protect` on all of these. Derive the target email/identity from req.user instead of trusting req.body.email; reject or ignore any body email that does not match req.user.email (unless the caller is an admin). Never set/overwrite passwords from an unauthenticated body field — password changes must go through an authenticated flow that verifies the current session owner. Restrict GET /register-details/:email to the owner or admin.
  - **Verification:** confirmed (confidence: high). Confirmed in code. None of the listed endpoints use the imported `protect` middleware (only /settings at lines 852/871 do). POST /register-details (line 71) destructures email+password from req.body (line 82), finds an existing user by that email (lines 147-148), and at lines 159-165 overwrites `user.password = password` and saves whenever a password is supplied — the pre-save hook hashes it, so any unauthenticated attacker can reset an arbitrary victim's password by posting their email, then log in via the unauthenticated POST /login (line 647). Full account takeover confirmed. PATCH /register-section (line 413) similarly mutates any user's record by email with no auth. GET /register-details/:email (line 745) accepts an arbitrary email param and returns the full Registration.toObject() (lines 774, 826) and full user object (lines 837/842) including badges, college, mobile, and login timestamps — unauthenticated PII disclosure for any email. The login endpoint being public is expected and doesn't itself constitute the vuln, but the password-overwrite + PII-read vectors are real and independently severe. Note: there is also a misplaced router.post('/_dev/backfill') nested inside the /register-details handler (lines 316-381), which is a separate code-smell but not part of this finding.

### 4. [CRITICAL] x-admin-bypass header grants full admin with no auth when ADMIN_SYSTEM_SECRET is unset
- **Category:** privilege-escalation
- **Location:** `back-end/middleware/roleMiddleware.js:6-18`
- **Problem:** requireRole accepts x-admin-bypass:true with x-admin-secret matching process.env.ADMIN_SYSTEM_SECRET and grants role 'admin'. Unlike middleware/auth.js (which wraps the bypass in `if (NODE_ENV !== 'production')`), this roleMiddleware bypass runs in ALL environments including production. If ADMIN_SYSTEM_SECRET is undefined, the comparison is `req.headers['x-admin-secret'] === undefined`, which is satisfied by simply omitting the x-admin-secret header — granting any caller full admin. Even when set, it is a static shared secret transmitted as a plain header with no rotation, IP allowlist, or expiry.
- **Fix:** Refuse the bypass entirely if ADMIN_SYSTEM_SECRET is falsy (`if (!adminSecret) return res.status(401)...`). Use a constant-time comparison (crypto.timingSafeEqual). Restrict to an internal IP allowlist and/or replace with a properly signed service JWT. Consider removing the header bypass from production paths altogether.
  - **Verification:** confirmed (confidence: high). Verified in back-end/middleware/roleMiddleware.js:6-18. requireRole grants role 'admin' and returns next() when x-admin-bypass:true and req.headers['x-admin-secret'] === process.env.ADMIN_SYSTEM_SECRET, with NO NODE_ENV guard — unlike the identical bypass in middleware/auth.js:15 which is wrapped in `if (process.env.NODE_ENV !== 'production')`. So this bypass executes in all environments including production. When ADMIN_SYSTEM_SECRET is unset, adminSecret is undefined and omitting the x-admin-secret header makes the comparison undefined === undefined (true), granting unauthenticated full admin. Reachable: requireRole is wired as a gate via router.use(requireRole('moderator','admin')) in routes/moderation.js:23 (warn/suspend/delete-post/escalate) and used in moderationQueue.js, community.js, ppiRoutes.js. Even when the secret is set, it is a static shared header secret with no rotation/expiry/IP allowlist. Critical severity confirmed.

## Section 4 — Deployment & Cybersecurity (AWS ECS + Docker, India)

**Stack decision — endorsed.** Docker containers on **AWS ECS Fargate** in **ap-south-1 (Mumbai)** is the correct, production-professional choice for an Indian launch. Mumbai has full service parity (Fargate, ALB, WAF, Secrets Manager, ACM, CloudFront edge); ap-south-2 Hyderabad does **not** — keep everything in ap-south-1. The frontend React SPA should be served from **S3 + CloudFront**, not from ECS. MongoDB should be **MongoDB Atlas on AWS Mumbai** (managed HA + backups), not self-managed.

**What is already good in your config:** a `.dockerignore` correctly excludes `.env`/keys/git from the image; the ECS task definition references **Secrets Manager ARNs** (not inline secrets); ACM gives free TLS; WAF/HTTPS guidance is present.

**Deployment-specific findings** (full detail in Sections 1–3 by severity; summarized here):

- 🔴 Live secrets committed to git (`back-end/.env`) — rotate + purge history.
- 🟠 `OPENROUTER_API_KEY` and SMTP creds used by the app are **not provisioned** in the ECS task definition — the app will fail or fall back insecurely in production.
- 🟠 JWT passed in the **WebSocket URL query string** — lands in ALB/CloudWatch access logs in plaintext. Move to the `Sec-WebSocket-Protocol` header or a short-lived ticket.
- 🟡 MongoDB Atlas reachable from the **entire VPC CIDR + NAT public IP**; restrict to the task security group only.
- 🟡 ECS container runs with a **writable root filesystem**; set `readonlyRootFilesystem: true` with a tmpfs for scratch.
- 🟡 CI/CD pushes the **mutable `:latest` tag** and does not gate deploy on the image vulnerability scan; pin to immutable digests and block on scan results.
- 🟡 ECS egress security group allows **unrestricted outbound 0.0.0.0/0**; scope to required destinations.
- 🟡 No ulimits/stop-timeout; **50MB JSON body limit on a 512MB task** invites OOM/DoS; lower the body limit and right-size resources.
- ⚪ WAF present but **no rate-limiting rule**; add a rate-based rule and enforce TLS 1.2+.

## Fargate vs EC2 — Recommendation

**Use Fargate for both launch and early production.** Rationale:

- **No cluster management.** A launch-stage company should not pay an engineer to patch/scale EC2 container hosts. Fargate removes EC2, AMI patching, and capacity planning.
- **Websockets are fine on Fargate** behind an ALB (long-lived connections supported; just tune idle timeout and use connection draining).
- **Cost crossover:** EC2 (especially with Savings Plans / Spot) becomes cheaper only at sustained high CPU/RAM (~8-15+ vCPUs running 24×7). Below that, Fargate's premium (~20-30% per vCPU-hr) is far cheaper than the engineering time EC2 costs.
- **When to switch to EC2:** once your steady-state compute exceeds roughly **8-10 vCPUs 24×7** and you can commit to a 1-yr Savings Plan, EC2 + Cluster Auto Scaling saves meaningful money. At ~5,000 users you are **not** there yet — stay on Fargate.
- **Cost lever regardless:** buy a **1-year Fargate Compute Savings Plan** for the always-on baseline (~30% off the steady tasks) once load is predictable.

## (C) What scales the cost — the real cost drivers

1. **MongoDB tier** — biggest single line item. M10→M30→M40 roughly doubles each step. Right-size by working-set RAM, not disk. Single largest lever in both tiers.
2. **CloudFront / data egress** — scales directly with media-heavy traffic and frontend bundle size. Offload media to Cloudinary (you already do) so CloudFront mostly serves the cached SPA. Egress is the #1 surprise bill at scale.
3. **Fargate task count** — autoscaling on websocket concurrency / CPU. Persistent websockets pin memory, so connections-per-task caps how low you scale. More concurrent users = more always-on tasks.
4. **NAT Gateway data processing** — every outbound AI/Cloudinary/email byte through NAT is billed (~$0.045/GB processed + hourly). Heavy AI payloads inflate this. Use a **VPC Gateway Endpoint for S3** (free) and consider interface endpoints only if they pay off.
5. **CloudWatch Logs ingestion** — verbose app/websocket logging silently balloons. Set retention (7-30 days) and sample debug logs.
6. **WAF requests** — scales with request volume; managed rule groups add per-rule + per-request cost.
7. **NOT on the AWS bill (track separately):** **OpenRouter/OpenAI** token spend (can dwarf all AWS costs — easily $200-$2,000+/mo depending on model and volume), **Cloudinary** plan (~$0-$224+/mo), and any **email** provider (SES is cheap at ~$0.10/1k; 3rd-party like SendGrid/Postmark is separate).

## Appendix A — Refuted findings (checked and dismissed)

These were flagged by a finder agent but **disproven** during code verification — listed for transparency:

**1. Authenticated mutation/upload fetch calls omit the Authorization header**  
Verifier note: The frontend code observations are accurate: Profile.jsx (lines 187, 220, 281, 461, 469, 522, 548, 589) and Settings.jsx (lines 101, 139) all issue PATCH /users/register-section and POST /upload with no Authorization header and no credentials:'include', while the GET at Profile.jsx:319 and Settings.jsx:64-65 does attach a Bearer token. However the finding's core CLAIM and predicted impact are FALSE. The backend route handler `router.patch('/register-section', async (req,res) => ...)` at back-end/routes/users.js:413 has NO auth middleware, and `router.post('/', ...)` in back-end/routes/uploadRoutes.js:10 has only a rate limiter (generalLimiter) and NO auth. So these endpoints do NOT require a token and will NOT return 401 — the saves/uploads succeed unauthenticated. The premise 'GET attaching a token proves the API expects it' is invalid: the GET attaches a token but the mutation endpoints don't enforce one. Thus 'every profile/settings save will be rejected (401)' is incorrect; the feature works. The actual real problem is the inverse — these mutation endpoints are unauthenticated on the server (broken access control / IDOR: any caller can PATCH any user's record by passing an arbitrary email), which the repo's own notes (full_commits.md: 'backend must enforce auth here') acknowledge. That is a genuine vuln but is a different finding from the one claimed. As stated (functional breakage via 401), the finding is refuted.

**2. Dockerfile bakes entire source tree and dev/native build toolchain into the runtime image**  
Verifier note: The finding's central claims are refuted by the actual code. (1) Secret leakage: a .dockerignore DOES exist at aws-deployment/.dockerignore and explicitly excludes .env, .env.backup, *.env, *.pem, *.key, credentials.json, .git/, front-end/, tests/, etc. The finding speculated the .dockerignore was "not shown/guaranteed" — it is present and comprehensive, so committed back-end/.env / .env.backup would NOT be baked into the image. (2) Dev/native toolchain in runtime: python3/make/g++/git are installed via `apk add` on line 8, which is in the BUILDER stage only (FROM ... AS builder). The runner stage (line 20, FROM node:20-alpine AS runner) starts from a fresh base and only does `COPY --from=builder` of node_modules and app files — it does NOT inherit the builder's apk-installed packages. So the toolchain is correctly discarded and is NOT in the production runtime image; this is exactly what the multi-stage split achieves. The only literally-true sliver is that `COPY . .` copies the whole context and the multi-stage size benefit is modest for a non-compiled Node app — but that is normal/benign, not a high-severity security issue, and even then is bounded by the .dockerignore exclusions. The finding mischaracterizes the runtime attack surface and the secret risk.

**3. India DPDP Act 2023 data-residency, processor obligations, and third-party transfers not addressed**  
Verifier note: Refuted on the code. The referenced files are a `.example` template plus an ECS task definition; both use placeholders and AWS Secrets Manager ARNs — there is NO leaked/committed secret (the claim's premise (4) and references to "the leaked URI's cluster region" are fabricated). The env header explicitly warns never to commit real credentials. Infra is consistently pinned to India's ap-south-1 (Mumbai): CloudWatch logs region, every Secrets Manager ARN, and SMTP host email-smtp.ap-south-1.amazonaws.com; the MongoDB URI shows a region placeholder, undercutting the "residency unspecified" point. The remaining DPDP items (cross-border AI transfers to OpenAI/OpenRouter, Cloudinary region not pinned, no documented retention/erasure) are legal/compliance/documentation governance gaps, not code defects — and CloudWatch "retains forever" is not set anywhere in code. Not a verifiable code vulnerability.
